# FRP Web Panel

[中文文档](./README.md)

FRP Web Panel is a self-hosted FRP management and monitoring platform. It is derived from `VaalaCat/frp-panel` and adapts the upstream project for Docker-first deployments, node operations, port visibility, traffic history, and Caddy-based HTTPS gateways.

The main workflow is intentionally centralized: an administrator manages Servers, Clients, Workers, tunnels, gateways, and certificates in the Master web UI; the UI generates copyable Docker Compose files for nodes; node health, logs, port snapshots, and traffic history are reported back to the Master.

## Features

- **Master control plane**: users, permissions, nodes, tunnels, certificates, gateways, statistics, and operational state.
- **Server management**: run and manage `frps`, generate a Server Compose file, and optionally run a Caddy HTTPS gateway on the same host.
- **Client management**: run and manage `frpc`, reach private services, and receive tunnel configuration from the Master.
- **Worker management**: keep Linux Worker creation, deployment, status, and ingress management available.
- **Tunnel management**: create, edit, delete, start, and stop tunnels; common TCP, UDP, HTTP, and HTTPS forms are available together with advanced FRP JSON configuration.
- **Node monitoring**: online state, heartbeat, latency, version, platform, connection time, and the latest listening-port snapshot.
- **Port checks**: show current TCP/UDP listeners on a node and compare them with platform-assigned ports before applying a tunnel.
- **Traffic history**: inspect inbound and outbound traffic for a tunnel over 1, 3, 7, or 30 days, or a custom date range.
- **Operations**: stream node logs in real time and open a remote terminal when the administrator has enabled remote Shell access.
- **Certificates and HTTPS**: register domains, choose a target Server and ACME challenge, and let Caddy issue, renew, and store certificates on that Server.
- **Docker-first deployment**: Master, Server, and Client use one image with a role-specific command; node Compose content is generated by the web UI.

## Architecture

```text
Browser
  |
  | Web/API
  v
Master (SQLite, node/tunnel/certificate/statistics control)
  |                         |
  | encrypted control        | generated Compose / pushed config
  v                         v
Server Agent + frps + Caddy  Client Agent + frpc + optional Worker
  |                         |
public FRP ports, 80/443     private service, for example 127.0.0.1:8880
```

### Network modes

| Component | Default network | Purpose |
| --- | --- | --- |
| Master | Docker bridge | Publishes the Web/API and RPC ports; keeps SQLite in persistent storage. |
| Server Agent + frps | Linux host | Binds FRP ports and shares the host listener space with Caddy. |
| Caddy | Linux host | Owns public ports 80/443 for ACME and HTTPS gateway traffic. |
| Client Agent + frpc | Linux host | Reaches services listening on the host network. |
| Worker | Worker runtime on a Linux node | Managed by the Client Agent; the initial target is Linux x86_64/ARM64. |

Server and Client Compose files use `network_mode: host`, so they do not add Docker `ports:` mappings. A bind failure is therefore a real host-port conflict. The Master Compose publishes `9000/tcp` for Web/API and `9001/tcp` for RPC by default.

## HTTPS Gateway and Certificates

The recommended HTTP tunnel path is:

```text
https://app.example.com:443
        -> Caddy on the target Server
        -> frps HTTP virtual-host port
        -> the selected Client HTTP tunnel
        -> the local service on :8880
```

This allows a local service on Client port `8880` to be exposed through an HTTP tunnel and served through Caddy on public port `443`. Caddy preserves the original `Host` header so `frps` can select the matching HTTP tunnel.

The certificate page supports:

- Registering one or more domains and selecting the target Server.
- Selecting the HTTP-01 or TLS-ALPN-01 ACME challenge.
- Starting a request, requesting again, and displaying renewal state.
- Binding a domain to an HTTPS Gateway route and showing Caddy apply errors.
- Keeping certificate private keys in the target Server's Caddy data directory instead of the Master database.

You must create the A/AAAA record yourself in Cloudflare or another DNS provider and point it at the target Server. The platform does not call the Cloudflare DNS API or change DNS records. HTTP-01 requires public TCP 80; TLS-ALPN-01 requires public TCP 443. Caddy must own those ports.

The Caddy container in the Server Compose listens on 80 (HTTP-01 challenge and HTTP redirect) and 443 through the configuration generated by the panel. No manual port mapping is needed in the Caddyfile or Compose file, but host ports 80/443 must not be used by the `frps` `vhostHTTPPort` or another process, and they must be allowed in the firewall/security group.

When a certificate request fails, open “View request history” in the Certificate Center to see the failure reason and jump to the target server's log page for the ACME details. Caddy writes its runtime log to `logs/caddy.log` in the Caddy data directory; the generated Server Compose mounts that directory read-only at `/caddy-data` inside the frp-panel container (it stays `/data` inside the Caddy container), so it never collides with frp-panel's own `/data` volume.

An FRP `type=https` tunnel is different: TLS is normally passed through to the Client-side service, which must manage its own certificate. It is not the same as terminating TLS in the Server-side Caddy gateway. Wildcard certificates and DNS-01 automation are not included in the initial scope. Public ACME issuance, renewal, browser trust, and real public 443 access still need to be verified by the deployer on a host with a public address.

## Docker Deployment

This section uses only the published Docker Hub image. No source checkout or local build is required. The Master is deployed from one Compose file, and Server/Client nodes are deployed from the Compose files the Master generates for them.

### Requirements

- Linux Docker Engine.
- Docker Compose v2 (`docker compose`).
- Linux is recommended for Server/Client nodes because they rely on host networking.

Master, Server, and Client share one image and select their role through the startup argument:

```text
lujuya/frp-web-panel:latest
```

The image is published for `linux/amd64`. To pin a version for rollback, replace `latest` in the Compose file with a concrete tag such as `lujuya/frp-web-panel:local-e5fb9832191e`.

### Deploy the Master

1. Create the deployment directory on the Master host:

```bash
sudo mkdir -p /opt/frp-panel
cd /opt/frp-panel
```

2. Generate a secret. `APP_GLOBAL_SECRET` encrypts node credentials, so keep it: a reinstall must reuse the same value.

```bash
openssl rand -hex 32
```

3. Put that value into `.env` (replace `REPLACE_WITH_THE_GENERATED_SECRET`). `MASTER_API_HOST` must be an IP or domain reachable from your browser and from every Server/Client node:

```bash
sudo tee /opt/frp-panel/.env >/dev/null <<'EOF'
COMPOSE_PROJECT_NAME=frp-panel
FRP_PANEL_CONTAINER_NAME=frp-panel-master
FRP_PANEL_IMAGE=lujuya/frp-web-panel:latest
MASTER_WEB_PORT=9000
MASTER_RPC_PORT=9001
APP_GLOBAL_SECRET=REPLACE_WITH_THE_GENERATED_SECRET
MASTER_API_HOST=192.0.2.10
MASTER_RPC_HOST=192.0.2.10
MASTER_API_SCHEME=http
CLIENT_API_URL=http://192.0.2.10:9000
CLIENT_RPC_URL=grpc://192.0.2.10:9001
EOF
sudo chmod 600 /opt/frp-panel/.env
```

| Variable | Purpose |
|---|---|
| `FRP_PANEL_IMAGE` | Image reference; change to a fixed tag to roll back |
| `MASTER_WEB_PORT` / `MASTER_RPC_PORT` | Host ports published by the Master |
| `MASTER_API_HOST` | Address the browser uses for Web/API |
| `MASTER_RPC_HOST` | Address nodes use for RPC |
| `CLIENT_API_URL` / `CLIENT_RPC_URL` | Connection URLs written into node Compose files; may be reverse-proxied HTTPS/WSS |

4. Write `docker-compose.yml`:

```bash
sudo tee /opt/frp-panel/docker-compose.yml >/dev/null <<'EOF'
name: ${COMPOSE_PROJECT_NAME:-frp-panel}

services:
  master:
    image: ${FRP_PANEL_IMAGE:?Set FRP_PANEL_IMAGE in .env}
    container_name: ${FRP_PANEL_CONTAINER_NAME:-frp-panel-master}
    restart: unless-stopped
    ports:
      - "${MASTER_WEB_PORT:-9000}:9000/tcp"
      - "${MASTER_RPC_PORT:-9001}:9001/tcp"
    environment:
      APP_GLOBAL_SECRET: ${APP_GLOBAL_SECRET:?Set APP_GLOBAL_SECRET in .env}
      APP_ENABLE_REGISTER: "false"
      MASTER_API_HOST: ${MASTER_API_HOST:?Set MASTER_API_HOST in .env}
      MASTER_API_PORT: "9000"
      MASTER_API_SCHEME: ${MASTER_API_SCHEME:-http}
      MASTER_RPC_HOST: ${MASTER_RPC_HOST:?Set MASTER_RPC_HOST in .env}
      MASTER_RPC_PORT: "9001"
      CLIENT_API_URL: ${CLIENT_API_URL:?Set CLIENT_API_URL in .env}
      CLIENT_RPC_URL: ${CLIENT_RPC_URL:?Set CLIENT_RPC_URL in .env}
      DB_TYPE: sqlite3
      DB_DSN: /data/data.db?_pragma=journal_mode(WAL)
      IS_DEBUG: "false"
    volumes:
      - ./data:/data
    healthcheck:
      test: ["CMD", "curl", "--fail", "--silent", "http://127.0.0.1:9000/login"]
      interval: 15s
      timeout: 5s
      start_period: 30s
      retries: 3
EOF
```

5. Validate and start:

```bash
cd /opt/frp-panel
sudo docker compose config --quiet
sudo docker compose pull
sudo docker compose up -d
sudo docker compose ps
```

6. Once the health check passes, open `http://<MASTER_API_HOST>:9000` and register the first administrator. The first registered user becomes the administrator and registration then closes (`APP_ENABLE_REGISTER: "false"`).

The Master publishes two ports:

- `9000/tcp` for Web/API, reachable from both browsers and nodes.
- `9001/tcp` for RPC, used by Server/Client nodes.

Behind a reverse proxy or CDN, point `CLIENT_API_URL` and `CLIENT_RPC_URL` at the URLs nodes actually reach, such as `https://panel.example.com` and `wss://panel.example.com`, then run `sudo docker compose up -d` to recreate the container.

Back up both `.env` and `data/`; they hold the secret and the SQLite database.

### Deploy a Server or Client

Nodes need neither source code nor a local build — only Docker and network access to the Master.

1. Sign in to the Master and create a node on the Servers or Clients page.
2. Open the node details and copy or download the generated `docker-compose.yml`.
3. On that node host, create a directory and save the Compose file:

```bash
NODE_DIR="$HOME/frp-server"   # use "$HOME/frp-client" for a Client node
mkdir -p "$NODE_DIR"
cd "$NODE_DIR"
umask 077
nano docker-compose.yml
chmod 600 docker-compose.yml
```

4. Validate and start:

```bash
cd "$NODE_DIR"
docker compose config --quiet
docker compose pull
docker compose up -d
docker compose ps
```

The generated Compose contains the node ID, connection secret, and Master API/RPC URLs, and pins the application image to `lujuya/frp-web-panel:latest` with `pull_policy: always`, so every `docker compose pull` or `up -d` fetches the newest published image.

A Server Compose also starts the official `caddy:2-alpine` and persists `./caddy`, `./caddy/data`, and `./caddy/config` next to the Compose file. **Keep that directory**: deleting Caddy data removes issued certificates and renewal state. HTTPS Gateway use requires host ports 80/443 to be available.

Confirm in the Master that the node is online with a current version and heartbeat. If a node stays offline, check in order:

- Compose logs: `docker compose logs --tail=100 -f`
- Whether the node can reach `MASTER_API_HOST:9000` and `MASTER_RPC_HOST:9001`
- Whether firewalls or security groups allow 9000 and 9001
- Whether the node's cached `latest` image is stale: `docker compose pull`

### Upgrade

Both the Master and nodes upgrade by pulling a new image; no source is required:

```bash
# Master host
cd /opt/frp-panel
sudo docker compose pull
sudo docker compose up -d

# Each Server/Client node
cd "$NODE_DIR"
docker compose pull
docker compose up -d
```

Back up the Master's `.env` and `data/` plus each node's Caddy data directory before upgrading.

If a release changes the node Compose structure (mount paths or startup arguments, for example), regenerate the Compose in the Master, replace the file in the node directory, and run `docker compose up -d`. Pulling alone does not update the Compose file itself.

To roll back to a fixed version, change `image` in the Compose file:

```yaml
image: lujuya/frp-web-panel:local-e5fb9832191e
```

### Build from source (optional)

Only clone the source when you need to modify code or build your own image:

```bash
git clone --branch main https://github.com/yunj-yun/frp-web-panel.git
cd frp-web-panel
./scripts/build-image.sh
```

The script derives a `local-<commit>` tag and also tags the image `latest` when loading locally, matching the node Compose files generated by the Master. Publishing to Docker Hub requires `docker login` first, then `--push` (add `--latest` to move `latest` as well):

```bash
./scripts/build-image.sh --tag local-<commit> --platform linux/amd64 --push --latest
```

`scripts/deploy-master.sh` remains available as a convenience wrapper for source-based deployments (it builds and loads the image, writes `.env` and the Compose file, and waits for the health check), but regular Docker deployments follow the manual Compose steps above.

See the [Docker deployment details](./deploy/README_zh.md) for the complete option reference.

## Nodes, Tunnels, and Ports

### Nodes

The node pages support creation, editing, deletion, and regeneration of deployment content. Server, Client, and Worker status includes online/offline state, connection time, version, platform, and error information. Workers remain in scope for Linux x86_64/ARM64 nodes.

### Tunnels

Choose a Client, Server, tunnel type, local address, local port, and remote port. TCP, UDP, HTTP, and HTTPS forms cover common FRP settings; advanced mode keeps the original FRP JSON and validates the structured configuration before saving. Editing or deleting a tunnel can affect a bound Gateway route or certificate.

For TCP/UDP tunnels, `remotePort` must be in range, must not be assigned twice in the platform, and should not appear in the latest node port snapshot. HTTP/HTTPS tunnels use the FRP HTTP virtual-host path and domain routing; a local `8880` is not directly bound to public `443`.

### Port-check limitations

The Agent first runs `ss -H -ltnup` and falls back to the system socket table when `ss` is unavailable. It reports protocol, listening address, port, process, and observation time. The Master keeps:

- The latest point-in-time listeners reported by a node.
- Platform-assigned or reserved ports.
- Ports that a pending configuration is expected to use.

A snapshot is an observation, not an operating-system lock. Another process can still claim a port after the check; the final authority is the bind and health result when the service starts.

## Traffic, Logs, and Remote Terminal

- Traffic is grouped by calendar day in the platform timezone.
- Quick filters cover 1, 3, 7, and 30 days; custom queries use the half-open interval `[start, end)`. A full day on October 7 is `10-07 00:00` through `10-08 00:00`.
- The statistics page shows inbound, outbound, total traffic, and daily rows, with Client, Server, and tunnel filters.
- The log page streams node and FRP/Worker logs in real time.
- The remote terminal creates a PTY session through the Master control channel. Disable it in production with `CLIENT_FEATURES_ENABLE_REMOTE_SHELL=false`, then restart the service.

## Configuration and Security

- Use a long random `APP_GLOBAL_SECRET`; the deployment script generates one automatically.
- `.env`, SQLite `data/`, generated node Compose files, and Caddy data may contain credentials or certificate state. Restrict their permissions and include them in backups.
- After the first registration, keep public registration disabled; the default Compose sets `APP_ENABLE_REGISTER=false`.
- Put the Master behind HTTPS when exposing it and configure API and RPC forwarding schemes correctly.
- Caddy must own 80/443 on a Server. FRP `bindPort`, the HTTP virtual-host port, and TCP/UDP `remotePort` must avoid existing host listeners.
- Never commit real domains, node secrets, JWTs, `.env` files, or Caddy private keys.

## Development

Recommended tools are Go 1.24, Node.js 20, and pnpm 9.15.9. The frontend lives in `www/`; its build output is copied into the Go service's static asset directory.

```bash
# Frontend development
cd www
pnpm install --frozen-lockfile
pnpm dev

# Production frontend build
pnpm build

# From the repository root, build release binaries without rebuilding the frontend
cd ..
./build.sh --skip-frontend
```

Pushing a `v*` tag optionally starts `.github/workflows/release.yml`, which creates a GitHub Release and publishes multi-platform images to GHCR; normal deployment uses `lujuya/frp-web-panel` on Docker Hub. To publish a Docker Hub image manually, run `scripts/build-image.sh --tag <tag> --platform linux/amd64 --push` after `docker login`. QEMU is only needed by the optional multi-platform publishing workflow. Useful pre-commit checks are:

```bash
git diff --check
bash -n scripts/build-image.sh scripts/deploy-master.sh install.sh
```

## Current Boundaries

- WireGuard networking pages, APIs, runtime components, and product documentation have been removed; FRP tunnels and Workers remain.
- Full host CPU, memory, and disk monitoring is not included; monitoring currently covers nodes, tunnels, ports, and traffic.
- The platform does not call the Cloudflare DNS API or modify A/AAAA records.
- Wildcard certificates and DNS-01 automation are not included.
- Public ACME issuance, renewal, browser trust, and real public 443 access still require validation by the deployer in a public network environment.
